# Checklist Specification v1.0 Implementation Plan

**Date:** 2026-05-26  
**Status:** Ready for Implementation  
**Version:** 1.0 (Breaking Changes from Draft)

---

## Executive Summary

This plan documents all decisions and implementation steps for updating the Checklist Specification v1.0. These changes address critical issues found during review and add essential features for real-world usage.

**Key Outcomes:**
- Token-efficient design (omit nulls, not explicit `null` values)
- Extensible via `ext` object for application-specific data
- Rich status tracking (4 states + completion timestamp)
- Proper recurrence support with start dates
- Robust dependency validation (no circular chains)

---

## Decisions Summary

| # | Feature | Decision | Rationale |
|---|---------|----------|-----------|
| 1 | **Null Handling** | Omit fields when empty | Saves tokens (~6-10 per field), aligns with LLM guidelines, matches JSON Schema |
| 2 | **Extensions** | Add `ext` object property | Clean namespace, future-proof, easy to validate, interoperable |
| 3 | **ID Uniqueness** | Global across all nesting levels | Prevents ambiguity, consistent `after` references, clear mental model |
| 4 | **Status Tracking** | Replace `done` with `status` enum | 4 states (todo, in-progress, done, cancelled), clearer semantics |
| 5 | **Completion Audit** | Add `completed` timestamp | Track when tasks finished, enable velocity metrics, audit trail |
| 6 | **Recurrence** | Add `DTSTART` to RRULE subset | Defines recurrence anchor, consistent with iCal, logical grouping |
| 7 | **Dependencies** | Prohibit all circular chains | Self-references, direct cycles, indirect cycles all invalid |

## Detailed Specifications

### 1. Omit Null Fields

**Current Issue:** README states defaults are `null`, but JSON Schema uses `type: "string"` (not nullable).

**Solution:** Change documentation to say fields are *omitted* when empty.

**Before:**
```json
{
  "desc": null,
  "created": null,
  "items": [{"id": "1", "text": "Task", "done": false}]
}
```

**After:**
```json
{
  "items": [{"id": "1", "text": "Task"}]
}
```

**Token Savings:** ~6-10 tokens per omitted field

**Fields Affected:**
- Checklist: `desc`, `created`, `modified`, `author`, `tags`
- Item: `due`, `tags`, `assignee`, `notes`, `recur`, `after`, `attach`

---

### 2. Extension Mechanism (`ext`)

**Location:** Both Checklist (root) and Item objects

**Schema:**
```json
"ext": {
  "type": "object",
  "additionalProperties": true,
  "description": "Application-specific extension data"
}
```

**Usage:**
```json
{
  "$spec": "checklist/1.0",
  "id": "proj-001",
  "title": "Project Launch",
  "ext": {
    "app": "MyTodoApp",
    "version": "2.1.0",
    "customField": "anything"
  },
  "items": [
    {
      "id": "1",
      "text": "Design review",
      "ext": {
        "color": "#FF5733",
        "estimatedHours": 2,
        "jiraTicket": "DESIGN-42"
      }
    }
  ]
}
```

**Rules:**
- `ext` is optional (omitted if empty)
- Any JSON-serializable values allowed inside
- Implementations MUST preserve unknown `ext` data during round-trips
- Future spec versions will NEVER use keys inside `ext`

---

### 3. Global ID Uniqueness

**Rule:** All item IDs must be unique across the entire document, including all nesting levels.

**Valid:**
```json
"items": [
  {"id": "1", "text": "Task 1"},
  {"id": "2", "text": "Task 2", "items": [
    {"id": "2.1", "text": "Subtask"}
  ]}
]
```

**Invalid (ID "1" appears twice):**
```json
"items": [
  {"id": "1", "text": "Task 1"},
  {"id": "2", "text": "Task 2", "items": [
    {"id": "1", "text": "Subtask"}  // ERROR: Duplicate ID
  ]}
]
```

**Validation:** Implementations MUST reject checklists with duplicate IDs.

### 4. Status Field (Replaces `done`)

**Change:** Remove boolean `done`, add string `status`

**Enum Values:**

| Value | Meaning | Use Case |
|-------|---------|----------|
| `todo` | Not started yet | Default state |
| `in-progress` | Actively working on it | Started but not finished |
| `done` | Completed successfully | Finished task |
| `cancelled` | Decided not to do it | Won't complete, no longer relevant |

**Schema:**
```json
"status": {
  "type": "string",
  "enum": ["todo", "in-progress", "done", "cancelled"],
  "default": "todo"
}
```

**Migration:**

| Old `done` | New `status` |
|------------|--------------|
| `done: false` or omitted | `status: "todo"` or omitted |
| `done: true` | `status: "done"` |

**Examples:**
```json
// Minimal - status omitted (defaults to "todo")
{"id": "1", "text": "Buy groceries"}

// Explicit status
{"id": "2", "text": "Write report", "status": "in-progress"}

// Completed
{"id": "3", "text": "Submit form", "status": "done"}

// Cancelled
{"id": "4", "text": "Old task", "status": "cancelled"}
```

**LLM Guideline Update:** Omit `status` when it's `todo` (default).

---

### 5. Completion Timestamp (`completed`)

**Purpose:** Track exactly when an item was marked as done.

**Schema:**
```json
"completed": {
  "type": "string",
  "format": "date-time",
  "description": "ISO 8601 timestamp when status became 'done'"
}
```

**Rules:**
- Only valid when `status: "done"`
- Should be set automatically when status transitions to "done"
- Can be omitted even when done (optional audit field)
- Format: ISO 8601 datetime (e.g., `2024-01-15T09:30:00Z`)

**Example:**
```json
{
  "id": "1",
  "text": "Launch website",
  "status": "done",
  "completed": "2024-01-15T09:30:00Z"
}
```

**Validation:** If `completed` is present, `status` SHOULD be `"done"` (warning if not).

### 6. Recurrence Start (`DTSTART`)

**Change:** Add `DTSTART` property to RRULE subset.

**Updated RRULE Subset:**

| Property | Required | Values | Description |
|----------|----------|--------|-------------|
| `FREQ` | ✅ | `DAILY`, `WEEKLY`, `MONTHLY`, `YEARLY` | Recurrence frequency |
| `DTSTART` | ❌ | ISO 8601 date/datetime | When recurrence begins |
| `INTERVAL` | ❌ | integer | Repeat every N periods (default: 1) |
| `BYDAY` | ❌ | `MO`, `TU`, `WE`, `TH`, `FR`, `SA`, `SU` | Day(s) of week |
| `BYMONTHDAY` | ❌ | 1-31 | Day(s) of month |
| `BYMONTH` | ❌ | 1-12 | Month(s) for yearly recurrence |
| `UNTIL` | ❌ | ISO 8601 date | End date |
| `COUNT` | ❌ | integer | Number of occurrences |

**Examples:**

```
FREQ=DAILY                                    # Every day from today
FREQ=DAILY;DTSTART=2024-01-15                 # Every day starting Jan 15
FREQ=WEEKLY;BYDAY=MO,WE,FR;DTSTART=2024-01-15 # Mon/Wed/Fri starting Jan 15
FREQ=MONTHLY;BYMONTHDAY=1;DTSTART=2024-01-01  # 1st of each month
FREQ=YEARLY;BYMONTH=3;BYMONTHDAY=15          # March 15 every year
FREQ=DAILY;COUNT=30;DTSTART=2024-01-01       # Daily for 30 occurrences
```

**Note:** `BYMONTH` added to support yearly recurrence on specific dates (e.g., March 15).

### 7. Circular Dependency Prevention

**Rule:** The `after` field MUST NOT create circular dependency chains.

**Invalid Patterns:**

1. **Self-reference:**
```json
{"id": "1", "text": "Task", "after": "1"}  // ERROR: References itself
```

2. **Direct cycle:**
```json
{"id": "1", "text": "A", "after": "2"},
{"id": "2", "text": "B", "after": "1"}   // ERROR: A→B→A
```

3. **Indirect cycle:**
```json
{"id": "1", "text": "A", "after": "2"},
{"id": "2", "text": "B", "after": "3"},
{"id": "3", "text": "C", "after": "2"}   // ERROR: B→C→B
```

**Validation Algorithm:**
```
For each item with `after`:
  1. Verify `after` references an existing item ID
  2. Follow the chain: current → after → after's after → ...
  3. If any ID appears twice, it's a circular dependency
  4. Reject the checklist if circular
```

**Cross-level references:** Allowed (can reference any item at any level), just no cycles.

## Migration Guide

### For Implementations (Apps/Libraries)

**Breaking Changes:**
1. Replace `done` boolean with `status` string
2. Handle 4 possible status values
3. Preserve new `ext` field during round-trips
4. Validate ID uniqueness globally
5. Detect circular `after` chains
6. Support `DTSTART` and `BYMONTH` in recurrence

**Migration Code Example:**
```javascript
// Old format → New format
function migrateItem(oldItem) {
  const newItem = {
    ...oldItem,
    status: oldItem.done ? "done" : "todo"
  };
  delete newItem.done;
  return newItem;
}
```

### For Users

**Before:**
```json
{"id": "1", "text": "Task", "done": true}
```

**After:**
```json
{"id": "1", "text": "Task", "status": "done"}
```

**New Capabilities:**
- Track when tasks were completed (`completed` timestamp)
- Mark tasks as in-progress or cancelled
- Add custom data via `ext` object
- Set recurrence start dates (`DTSTART`)
